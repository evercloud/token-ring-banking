Sistema di transazioni bancarie distribuite con mutua esclusione a Token Ring

Corso: Intelligenza Artificiale Distribuita
Docente: Prof. Ala Arman
Studente: Claudio Scamporlino
Matricola: omessa nella versione pubblicata

Questo repository contiene l'implementazione sviluppata per un esame universitario di Intelligenza Artificiale Distribuita. Quattro processi ATM su localhost condividono un saldo bancario e coordinano gli aggiornamenti con l'algoritmo Token Ring per la mutua esclusione distribuita. Il progetto illustra scambio di messaggi, sezioni critiche e topologia ad anello — non è un sistema bancario di produzione.

1. Linguaggio e ambiente

Il progetto è scritto in TypeScript e compilato a JavaScript per essere eseguito su Node.js 20 o successivo. La comunicazione tra i nodi usa esclusivamente il modulo standard node:net (TCP) e non richiede librerie di rete o di concorrenza esterne. È stato sviluppato e testato su macOS.

2. Dipendenze

Il progetto non ha dipendenze a runtime. Le dipendenze di sviluppo, inserite nel package.json, sono:

  • typescript — compilatore tsc;
  • @types/node — tipi delle API di Node;
  • tsx — usato solo dallo script npm run dev in watch mode, non necessario all'esecuzione.

Installazione, una sola volta, dalla radice del repository:

npm install

3. Compilazione

Per compilare, lanciare dalla radice del repository:

npm run build

Viene eseguito tsc e generata la cartella dist/. Il punto d'ingresso di ciascun nodo ATM è dist/main.js.

4. Modello di esecuzione

Il sistema è composto da quattro nodi (ATM1, ATM2, ATM3, ATM4), ciascuno avviato come processo distinto del sistema operativo. La coordinazione fra nodi avviene solo tramite scambio di messaggi su 127.0.0.1:

  • ATMk ascolta sulla porta 4000 + k (ATM1 sulla 4001, ATM2 sulla 4002, ecc.);
  • l'anello logico è ATM1 → ATM2 → ATM3 → ATM4 → ATM1; ogni nodo conosce esclusivamente il proprio successore;
  • ATM1 è il nodo iniziale del ring: inietta il primo token dopo aver stabilito le connessioni. In avvio manuale è consigliabile avviarlo per ultimo, in modo che gli altri nodi siano già in ascolto.

Ogni nodo mantiene la propria copia privata del saldo. La mutua esclusione sull'aggiornamento è garantita dal possesso del token: solo il nodo che ha ricevuto il token può eseguire una transazione e modificare il saldo, prima di inoltrare il token al successore con il valore aggiornato.

5. Avvio dei quattro nodi

Per un avvio manuale, i quattro nodi vanno lanciati in quattro terminali distinti, dalla radice del repository, dopo npm install e npm run build. La tabella seguente mostra come lanciare i quattro nodi per eseguire l'esempio delle specifiche di progetto: saldo iniziale 1000, ATM2 prelievo 200, ATM3 deposito 100, ATM4 prelievo 500, saldo finale 400.

Terminale Processo Comando
1 ATM2 node dist/main.js --atm 2 --withdraw 200
2 ATM3 node dist/main.js --atm 3 --deposit 100
3 ATM4 node dist/main.js --atm 4 --withdraw 500
4 ATM1 node dist/main.js --atm 1

Più operazioni sullo stesso ATM si accodano ripetendo le opzioni sulla stessa riga di comando, ad esempio --atm 2 --withdraw 200 --deposit 50: vengono eseguite una per giro del token, in ordine FIFO.

In alternativa, lo script run-demo.sh (richiamabile anche come npm run demo) avvia i quattro processi con un singolo comando, stampando i PID a inizio esecuzione per evidenziare che si tratta di quattro processi UNIX distinti. Ctrl+C li chiude tutti insieme.

6. Comportamento atteso

Le transazioni vengono gestite in mutua esclusione dal passaggio del token sull'anello: ATM2 esegue il prelievo (saldo 800), ATM3 il deposito (900), ATM4 il prelievo finale (400). Il saldo finale è 400. I log di ciascun nodo riportano la ricezione del token, l'inizio e la fine di ciascuna transazione, il saldo aggiornato e l'inoltro del token al successore. Ho prefissato tutti i messaggi con l'identificatore del nodo ([ATM1], …, [ATM4]), così resta leggibile la circolazione del token e il saldo anche quando l'output dei processi si mescola nella stessa console. Tra la fine della sezione critica e l'inoltro del token al successore è inserita una piccola pausa configurabile (FORWARD_DELAY_MS in config.ts, default 500ms) al solo scopo di rendere più leggibile la circolazione del token nei log. Il valore può essere portato a 0 per ottenere l'inoltro immediato previsto dalle specifiche di progetto.

7. Terminazione coordinata

Le specifiche di progetto prevedono che il token circoli continuamente. Durante i test ho scelto di aggiungere una rilevazione di terminazione distribuita: il messaggio TOKEN porta, oltre al saldo, un contatore idleHops degli hop consecutivi del token senza operazioni in coda da elaborare. Ogni nodo lo incrementa se la propria coda è vuota e lo azzera se ha un'operazione in coda da elaborare. Quando idleHops raggiunge 4 (cioè un giro completo dell'anello con tutte le code vuote), il nodo che rileva la soglia immette nel ring un messaggio DONE marcato con il proprio identificatore; il DONE percorre l'anello e fa uscire ordinatamente tutti i nodi.

È importante notare che il protocollo basato sul TOKEN non cambia. Il DONE è un'estensione progettuale per non lasciare il ring in esecuzione perpetua: è un messaggio introdotto per studiare un caso elementare di terminazione distribuita coordinata e per ottenere una chiusura ordinata dei processi, migliorando la leggibilità dei risultati.

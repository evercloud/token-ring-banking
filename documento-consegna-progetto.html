This repository contains the coursework implementation developed for a university exam in Distributed Artificial Intelligence. Four ATM processes on localhost share a bank balance and coordinate updates with the Token Ring algorithm for distributed mutual exclusion. The project demonstrates message passing, critical sections, and ring topology — it is not production banking software.

1. Language and environment

The project is written in TypeScript and compiled to JavaScript to run on Node.js 20 or later. Communication between nodes uses only the standard node:net module (TCP) and does not require external networking or concurrency libraries. It was developed and tested on macOS.

2. Dependencies

The project has no runtime dependencies. Development dependencies, listed in package.json, are:

  • typescript — tsc compiler;
  • @types/node — Node API type definitions;
  • tsx — used only by the npm run dev script in watch mode, not required at runtime.

Install once from the repository root:

npm install

3. Build

From the repository root, run:

npm run build

This runs tsc and produces the dist/ folder. The entry point for each ATM node is dist/main.js.

4. Execution model

The system consists of four nodes (ATM1, ATM2, ATM3, ATM4), each started as a separate operating-system process. Coordination between nodes happens only through message exchange on 127.0.0.1:

  • ATMk listens on port 4000 + k (ATM1 on 4001, ATM2 on 4002, etc.);
  • the logical ring is ATM1 → ATM2 → ATM3 → ATM4 → ATM1; each node knows only its successor;
  • ATM1 is the initial ring node: it injects the first token after connections are established. In manual startup it is advisable to start it last, so the other nodes are already listening.

Each node maintains its own private copy of the balance. Mutual exclusion on updates is enforced by token possession: only the node holding the token can execute a transaction and modify the balance, before forwarding the token to its successor with the updated value.

5. Starting the four nodes

For manual startup, the four nodes must be launched in four separate terminals from the repository root, after npm install and npm run build. The table below shows how to start the four nodes to run the project specification example: initial balance 1000, ATM2 withdraw 200, ATM3 deposit 100, ATM4 withdraw 500, final balance 400.

Terminal Process Command
1 ATM2 node dist/main.js --atm 2 --withdraw 200
2 ATM3 node dist/main.js --atm 3 --deposit 100
3 ATM4 node dist/main.js --atm 4 --withdraw 500
4 ATM1 node dist/main.js --atm 1

Multiple operations on the same ATM are queued by repeating the options on the same command line, for example --atm 2 --withdraw 200 --deposit 50: they are executed one per token lap, in FIFO order.

Alternatively, the run-demo.sh script (also available as npm run demo) starts all four processes with a single command, printing PIDs at startup to show that these are four distinct UNIX processes. Ctrl+C shuts them all down together.

6. Expected behavior

Transactions are handled under mutual exclusion as the token travels around the ring: ATM2 performs the withdrawal (balance 800), ATM3 the deposit (900), ATM4 the final withdrawal (400). The final balance is 400. Each node's logs report token reception, the start and end of each transaction, the updated balance, and token forwarding to the successor. All messages are prefixed with the node identifier ([ATM1], …, [ATM4]), so token circulation and balance updates remain readable even when process output is interleaved in the same console. A small configurable pause between leaving the critical section and forwarding the token (FORWARD_DELAY_MS in config.ts, default 500ms) is inserted solely to make token circulation easier to follow in the logs. The value can be set to 0 for immediate forwarding as specified in the project requirements.

7. Coordinated termination

The project specification requires the token to circulate continuously. During testing I chose to add distributed termination detection: the TOKEN message carries, in addition to the balance, an idleHops counter of consecutive token hops with no queued operations to process. Each node increments it if its queue is empty and resets it if it has an operation to process. When idleHops reaches 4 (i.e. a full ring lap with all queues empty), the node that detects the threshold injects a DONE message into the ring marked with its own identifier; DONE travels around the ring and shuts down all nodes in order.

It is important to note that the TOKEN-based protocol does not change. DONE is a design extension to avoid leaving the ring running indefinitely: it is a message introduced to study a basic case of coordinated distributed termination and to obtain an orderly process shutdown, improving the readability of results.
